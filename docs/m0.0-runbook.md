## Steps 1–4 — install (script encodes the guide)

```bash
export KUBECONFIG=~/.kube/config.ocp5-1
./scripts/m0.0-install-openshell.sh
```

**Deviations from the guide** (logged for the M0.0 milestone memory):
- **Chart**: vendored gateway-chart **0.1.2** (copied to `deploy/chart/charts/openshell/` from
  rhoai-cluster-pool, name normalized) instead of `oci://ghcr.io/nvidia/...:0.0.116` — ghcr
  anonymous OCI fetch 403s (COCO.md-documented); this copy is ArgoCD-proven on coco/prelude spokes.
- **Gateway image**: `quay.io/eformat/openshell-gateway:0.1.2-deadline.2` (public patched
  build — provisioning repair window + deadline patch); supervisor stays on chart-default ghcr
  (node image pulls from ghcr work; only chart FETCH was blocked).
- **fsGroup/runAsUser**: chart defaults (1000) kept — the privileged-SCC path has no range
  restriction (the coco overlay's range-pinning was a restricted-v2 constraint). Spike (f)
  measures the real sandbox UID regardless.
- **agentSandbox.preflight.enabled=false** — the chart's CRD lookup breaks offline/first renders
  (coco overlay gotcha); the runbook's step 0 checks the CRD instead.
- **Route + ns + SCC as chart templates** (GitOps-clean) rather than `oc create route` /
  bare `oc adm` — RoleBinding to `system:openshift:scc:privileged` is the RBAC equivalent.

What it does, in guide order:
1. **ns + SCC** — `openshell` ns; `privileged` SCC → `openshell-sandbox` SA **before** chart
   install (supervisor needs netns + nftables + Landlock; ordering is load-bearing). Our chart
   renders this as a RoleBinding (GitOps-clean equivalent of `oc adm policy add-scc-to-user`).
2. **helm install** — vendored 0.1.2 subchart (see deviations), Red Hat image tags from the guide
   still work as values overrides if needed.
3. **Route** — passthrough `openshell-openshell.<apps-domain>` → svc `openshell:8080`
   (mTLS terminates inside the gateway pod), rendered by the chart.
4. **Verify** — gateway pod Ready.

> **helm gotcha (hit in M0.0)**: `helm template` templates may call `lookup` against the live
> cluster — always pass `-n <namespace>` and be deliberate about the exported KUBECONFIG when
> rendering, or you get cluster-derived values leaking into offline renders.

## Steps 5–7 — laptop-side connect

```bash
umask 077
mkdir -p ~/.config/openshell/gateways/openshift/mtls
oc -n openshell get secret openshell-client-tls \
  -o jsonpath='{.data.ca\.crt}'  | base64 -d > ~/.config/openshell/gateways/openshift/mtls/ca.crt
oc -n openshell get secret openshell-client-tls \
  -o jsonpath='{.data.tls\.crt}' | base64 -d > ~/.config/openshell/gateways/openshift/mtls/tls.crt
oc -n openshell get secret openshell-client-tls \
  -o jsonpath='{.data.tls\.key}' | base64 -d > ~/.config/openshell/gateways/openshift/mtls/tls.key
chmod 700 ~/.config/openshell/gateways/openshift/mtls
chmod 600 ~/.config/openshell/gateways/openshift/mtls/tls.key

openshell gateway add "https://openshell-openshell.<apps-domain>" --local --name openshift
openshell status   # expect: Connected, Version 0.0.116-rhaiv.0
```

## Troubleshooting (guide + cluster memory + M0.0 live findings)

- Gateway `CreateContainerConfigError`/`Pending` → SCC binding didn't precede install;
  delete the pod to restart after fixing.
- Cert validation error → `pkiInitJob.serverDnsNames` must contain the exact Route host.
- `Too many pods` → maxPods=500 KubeletConfig is live on ocp5-1 (verified 2026-11-05);
  if pods-alloc ever shows 250 again, check the MCO render.
- `oc get subscription` resolves to ACM's API — use `oc get subscriptions.operators.coreos.com`.
- **Helm ownership collision** (`Namespace "openshell" ... cannot be imported into the current
  release`): the ns is created by the script (guide ordering); the chart must NOT ship a
  Namespace template. (Fixed: removed from templates.)
- **Gateway pod Forbidden by restricted-v2** (`fsGroup 1000 not allowed; runAsUser 1000 must be
  in [1001030000,1001039999]`): chart defaults 1000 don't fit the ocp5-1 ns range — values pin
  `podSecurityContext.fsGroup`/`securityContext.runAsUser` to `1001030000`. Also: the release
  prefix renames the SAs — use `fullnameOverride: openshell` so the privileged-SCC RoleBinding
  subject (`openshell-sandbox`) actually exists and the Route targets svc `openshell`.
- **Sandbox pod ImagePullBackOff on `supervisor:v0.0.116-rhaiv.0`** (manifest unknown): that's
  the Red Hat quay tag on the ghcr repo — introduced by the guide's
  `--set image.tag/supervisor.image.tag=$ODH_IMAGE_TAG` syntax against the vendored 0.1.2 chart.
  Values now pin `supervisor.image.tag: "0.1.2"`; the script no longer sets image tags.
- **`openshell` CLI not on PATH / installer needs sudo**: the agent-ops wrapper verifies pinned
  checksums then does `sudo rpm -i`. Passwordless-less path: download the release RPMs from
  GitHub (verify against `openshell-checksums-sha256.txt`), `rpm2cpio | cpio -idm`, copy
  `usr/bin/openshell` → `~/.local/bin`. Server 0.1.2 works with CLI 0.0.116 **and** 0.1.3.
- **Workload pod dies with `decode boundary config boundary.json: unknown field 'outer_fence'`**
  (any workload image — the reader is the INJECTED runtime, not the image): image-version skew.
  The supervisor pod writes `boundary.json`; the workload-side `openshell-sandbox --bootstrap`
  binary (injected from the `sandboxRuntime` image) reads it. The ghcr tag LIST is
  incomplete/truncated — `sandbox:0.1.2` and `supervisor:0.1.2` DO exist (verify with a
  manifest GET, not the list). Fix: pin **both** `supervisor.image.tag` and
  `sandboxRuntime.image.tag` to the chart-family version (`0.1.2`). Do NOT use `:dev`
  (older schema on both sides — the supervisor:dev rejects even the gateway's descriptor),
  and do NOT use the guide's `v0.0.116-rhaiv.0` tag (Red Hat quay build, absent on ghcr).
  Symptom when supervisor/sandbox skew the OTHER way (supervisor:dev + gateway 0.1.x):
  supervisor pod errors with `decode sandbox runtime descriptor: unknown field 'outer_fence'`.
  Long-term: pin digests per release once we control image builds.
- **`openshell gateway add` may rewrite the mtls bundle** (observed: dir mtime bumped, ca.crt
  replaced with a different CA → `invalid peer certificate: BadSignature` on `openshell status`).
  Re-extract the bundle from `secret openshell-client-tls` AFTER `gateway add` if status fails.
  Sanity: `openssl s_client -connect <route-host>:443 -CAfile <mtls>/ca.crt` → `Verify return
  code: 0 (ok)`.
- **`helm template` may query the live cluster** (templates call `lookup`): always pass
  `-n <namespace>` and mind the exported KUBECONFIG, or cluster-derived values leak into
  offline renders.

## M3.5 live gate (2026-11-06) — provider/egress lessons

- **Sandbox egress is OPA binary-identity enforced**: a provider profile's
  `endpoints:` are reachable ONLY by binaries listed in its `binaries:` — and only
  for processes spawned under the supervisor (platform `openshell sandbox exec`
  or the workload main process). `oc exec`-spawned processes are OUTSIDE the
  identity regime: they get no provider env and egress-deny regardless of profile.
- **Binary identity = the path that was executed**. `opencode` lives at
  `/usr/local/sbin/opencode` (3 hardlinks) but PATH resolves `/usr/local/bin/opencode`,
  and OPA reports THAT path. Whitelist every hardlink (`/usr/local/bin/opencode`
  AND `/usr/local/sbin/opencode`) or TCP gets refused (`transparent_tcp_policy_denied`
  in the supervisor log — the authoritative denial record; read it before guessing).
- **Provider profile update is export→edit→update**: `profile update` requires the
  current `resource_version` (`profile export openai -g openshift`, edit, update);
  `profile import` fails with "already exists" for a live ID. Then re-run
  `sandbox provider attach` to push a fresh receipt, and confirm the supervisor
  picked it up: `Policy reloaded successfully [policy_hash:…]` in
  `oc logs os-supervisor-<sandbox-id>`.
- **The workload phase must be Ready for `sandbox exec`** — the M0 probe's
  `exec sleep 1800` expires after 30 min and the sandbox drops to phase Completed
  (oc exec still works; platform exec refuses). `openshell sandbox start sync-oc
  -g openshift` relaunches the workload (M4: the real workload spec replaces the probe).
- **Env injection asymmetry**: `oc exec env ...` works for plain env; the provider
  credential reaches only supervisor-spawned processes (launch environment).
  The M3.5 gate used oc exec + explicit `OPENAI_API_KEY` env + platform policy for
  egress — key never persisted to the PVC or git.
- **Gateway map**: `openshell` gateway = coco cluster (OIDC, was down);
  `openshift` gateway = ocp5-1 (mtls, NO OIDC) — the sync-agent-pvc provider
  lives on the mtls gateway. `openshell sandbox list/get/exec -g openshift`.
- **The in-pod resolver (127.0.0.53) is policy-aware**: non-allowed binaries get
  EAI_AGAIN for unapproved names; allowed identities get real resolution.
  `ECONNREFUSED` from a whitelisted binary = wrong binary path in `binaries:`.
